# M8 考勤管理

> **模块定位**：核心教务层（P0），左侧菜单独立顶层，高频操作区。统一管理签到打卡和请假。
> **后端包**：`edu-module-attendance`
> **优先级**：P0，Phase 3 开发
> **使用端**：PC 后台（运营主管 / 教师 / 校长）+ 微信小程序（教师签到 Tab + 家长请假入口 + 家长通知接收）

---

## 1. 模块概述

考勤管理是教务闭环的关键环节，承上启下连接排课（M5）、学员（M3）、班级（M4）、教师（M2）四个模块。核心解决两个问题：

1. **签到**：教师每天对学生到校情况进行标记，确保出勤数据准确可追溯，并实时通知家长
2. **请假**：学生请假（家长发起 / 教师确认）和教师请假（发起 / 审批 / 冲突处理）两条完整流程，保障教学秩序

模块通过微信订阅消息打通家校互通，让家长实时了解孩子到校安全，让教师和主管高效处理异常出勤。

### 1.1 核心价值

| 角色 | 价值 |
|------|------|
| **家长** | 实时收到孩子到校/迟到/缺勤通知，安心放心；小程序一键请假，无需电话沟通 |
| **教师** | 小程序批量签到，秒级完成；代学生请假/自行请假流程清晰 |
| **运营主管** | PC 端统一管理签到记录和请假审批，教师请假冲突自动检测并逐节处理 |
| **校长** | 审批教师请假，掌握整体出勤状况 |

### 1.2 与关联模块的数据流

```
M5 排课管理 ──排课记录──→ M8 考勤管理（签到依据）
M3 学员管理 ←──签到/请假记录──→ M8 考勤管理（关联学生 + 课时变动）
M4 班级管理 ←──签到按班级批量操作──→ M8 考勤管理
M2 教师管理 ←──教师请假关联──→ M8 考勤管理
微信小程序 ←──签到操作 + 请假申请 + 通知推送──→ M8 考勤管理
M10 工作台 ←──今日到校/请假统计──→ M8 考勤管理
```

**三种冲突处理方式**：

| 处理方式 | 触发条件 | 操作 | 通知 |
|---------|---------|------|------|
| **代课** | 选择可授该科目的其他教师 | 替换排课教师 → 排课状态改为"代课" | 代课教师 + 受影响家长 |
| **调课** | 将排课改到新时间/教室 | 更新排课时间/教室 → 排课状态改为"调课" | 受影响家长 |
| **停课** | 直接取消本次排课 | 排课状态改为"停课" → 标记"待补课" | 受影响家长 |

**代课教师选择规则**：
- 下拉列表仅显示「可授该科目」且「该时段空闲」的教师
- 过滤掉请假教师本人
- 排序：按教师当前排课数量升序（课少的优先）

**每节冲突课必须逐节处理完毕，不可跳过。全部处理完成后，该请假单状态变为"已处理"。**

|------|------|

- 点击后 loading 状态，成功后不可再次点击

## 6. 教师请假流程

### 6.1 教师端发起

**小程序端（教师本人）**：
```
教师打开小程序 → 我的 Tab → 请假申请
  → 选择请假日期（支持多天选择）
  → 选择请假类型（事假/病假/其他）
  → 填写原因
  → 提交 → 状态：待审批
  → 通知管理员（校长/运营主管）审批
```

**PC 端（教师本人或运营主管代申请）**：
```
考勤管理 → 教师请假列表 → 点击「+ 教师请假申请」
  → 弹窗表单：
    - 选择教师（运营主管代申请时可选择；本人自动填充）
    - 选择请假日期（支持范围选择）
    - 选择请假类型
    - 填写原因
  → 提交 → 状态：待审批
```

### 6.2 管理员审批

```
校长/运营主管登录 PC → 考勤管理 → 教师请假列表
  → 筛选"待审批"
  → 查看请假详情
  → 审批操作：
    【通过】
      → 状态变为"已通过"
      → 系统自动检测该教师请假日期内所有排课冲突
      → 生成冲突排课列表
      → 通知教师（请假已通过）+ 提醒管理员处理冲突
      → 进入冲突处理流程

    【驳回】
      → 填写驳回原因（必填）
      → 状态变为"已驳回"
      → 通知教师（请假已驳回 + 驳回原因）
```

**管理员小程序端审批**：
- 校长/主管小程序 → 消息 Tab → 待审批列表
- 可查看教师请假详情 + 冲突预判（有多少节排课受影响）
- 支持通过/驳回操作

### 6.3 冲突检测与处理

**审批通过后自动检测**：
1. 查询教师请假日期范围内所有排课记录（状态为"正常"的排课）
2. 列出所有冲突排课，按时间排序
3. 每节冲突课必须逐节处理

**三种处理方式**：

#### 6.3.1 代课

```
前置条件：存在其他可授该科目的教师，且该时段空闲

操作步骤：
1. 在冲突排课行选择「代课」处理方式
2. 系统自动筛选可代课教师列表：
   - 可授该科目（教师档案中可授科目包含该课程科目）
   - 该时段无排课冲突（同教师同时段无其他排课）
   - 非请假教师本人
3. 选择代课教师 → 点击「确认代课」
4. 系统执行：
   - 原排课 teacher_id 替换为代课教师 → 状态改为"代课"
   - 发送微信订阅消息给代课教师（通知代课安排）
   - 发送微信订阅消息给该班所有学生家长（通知教师变更）

业务规则：
- 如果找不到合适的代课教师，该冲突排课必须选择「调课」或「停课」
- 代课教师的选择支持按当前课量排序（课少的优先）
```

#### 6.3.2 调课

```
操作步骤：
1. 在冲突排课行选择「调课」处理方式
2. 设置新日期 + 新时段 + 新教室（可选）
3. 系统做冲突检测：新时间新教师（原教师不变，调课后原教师可上课）
   - 注：调课后排课的教师仍是原教师（已请假教师），但新时间在其请假范围外
   - 调课后仍需检测新时间的教室冲突
4. 点击「确认调课」
5. 系统执行：
   - 排课日期/时间/教室更新 → 状态改为"调课"
   - 原时段标记为"已调课"
   - 发送微信订阅消息给该班所有学生家长（通知时间变更）

注意：
- 调课后的新日期必须不在此次请假范围内
- 调课后保留原教师，不更换授课教师
```

#### 6.3.3 停课

```
操作步骤：
1. 在冲突排课行选择「停课」处理方式
2. 点击「确认停课」
3. 系统执行：
   - 排课状态改为"停课" → 标记"待补课"
   - 发送微信订阅消息给该班所有学生家长（通知本次停课 + 后续补课另行通知）

后续处理（不在本次流程中，后续由运营主管在排课管理 M5 中操作）：
- 为该班级安排补课（新增一条排课记录，状态为"补课"，关联原停课排课 ID）
```

## 7. 课时返还规则

### 7.1 规则定义

学生请假审批通过后，系统根据配置判断是否返还该学生对应课时。

| 配置项 | 默认值 | 说明 |
|------|:--:|------|
| `attendance.leave.free_limit` | 3 | 每学期每学生前 N 次请假不扣课时 |
| `attendance.leave.free_limit.enabled` | true | 是否启用免费请假次数 |

配置项存储在 M0 系统配置中（`application.yml` 或数据库配置表），支持运营主管动态调整。

### 7.2 判断逻辑

```
学生请假审批通过
  │
  ├── 统计当前学期该学生的请假通过次数
  │
  ├── 本次次数 ≤ 免费额度？
  │     ├── 是 → 不扣课时
  │     │        标记签到为"请假"
  │     │        课时变动记录类型：请假返还
  │     │        学生课时不变
  │     │
  │     └── 否 → 正常扣课时
  │              标记签到为"请假"
  │              课时变动记录类型：请假扣课时
  │              学生对应班级剩余课时 -1
  │
  └── 学生有多个班级排课在同一天的情况：
        - 请假日期当天该学生所有排课均标记为"请假"
        - 课时返还按排课次数计算（每节排课算 1 次请假）
        - 例如：当天有 2 节数学课，免费额度剩余 2 次，则 2 节都不扣
        - 如果免费额度剩余 1 次，只有 2 节排课超过额度，则第 1 节不扣、第 2 节扣
```

### 7.3 课时变动明细

学生请假通过后，课时变动记录写入 M3 学员管理的课时明细表。

| 变动类型 | 说明 | 课时变化 |
|---------|------|:--:|
| 请假返还 | 在免费额度内，不扣课时 | 0 |
| 请假扣课时 | 超出免费额度，正常扣课时 | -1 |

**学期定义**：
- 第一学期：3月1日 - 7月31日
- 第二学期：9月1日 - 1月31日
- 免费额度按学期重置

### 7.4 边界情况

| 场景 | 处理 |
|------|------|
| 请假当天有多节排课 | 每节排课单独判断，共用同一免费额度池 |
| 请假申请跨多天 | 每天每个排课单独判断，提交时展示预期影响：「共涉及 N 节课，其中 M 节在免费额度内」 |
| 免费额度用完后又取消请假 | 课时已扣则不恢复；如教师驳回→不涉及课时变动 |
| 家长在免费额度内请假后又取消 | 该次请假释放额度（学生请假状态改为"已撤销"时恢复额度计数） |
| 学期切换 | 新学期开始，所有学生免费额度重置为配置值 |
| 配置变更 | 免费额度配置变更后，对已通过的请假不影响；仅对新请假生效 |

| T10 | 代课通知（给家长） | 代课处理确认后 | 家长 | "课程变更：xxx课程 教师变更为 xxx老师，时间不变" |

| T12 | 停课通知（给家长） | 停课处理确认后 | 家长 | "课程通知：xxx课程 本次停课（日期：xxxx-xx-xx），补课时间另行通知" |

### 8.2 订阅消息授权

- 小程序端使用微信订阅消息机制，用户需授权才能接收通知
- 家长端：首次打开小程序时引导授权，或在「通知设置」中管理
- 教师端：首次打开小程序时引导授权
- 每次签到/请假操作前，检查用户是否已授权对应模板消息，未授权则引导授权
- 单次授权支持一次推送（微信限制），需每次操作前重新授权（或使用长期订阅）

### 8.3 通知失败处理

| 情况 | 处理 |
|------|------|
| 用户未授权订阅 | 静默跳过，不阻塞签到/请假主流程 |
| 微信接口调用失败 | 记录失败日志，重试 1 次（间隔 5s），仍失败则标记"通知失败" |
| 用户取消订阅 | 静默跳过，家长可在「通知设置」中重新开启 |
| 批量通知部分失败 | 单独记录每条失败的通知，支持手动重发（P2） |

### 8.4 通知发送优先级

| 优先级 | 消息类型 | 允许延迟 |
|:--:|---------|:--:|
| 高 | T1 签到通知、T2 迟到通知、T3 缺勤通知 | ≤ 1 分钟 |
| 中 | T4-T6 请假通知、T7-T8 审批通知 | ≤ 5 分钟 |
| 中 | T9-T12 代课/调课/停课通知 | ≤ 5 分钟 |

## 9. 状态处理一览

### 9.1 签到状态

| 状态值 | 含义 | 触发方式 | 可变更 |
|:--:|------|---------|:--:|
| 到校 | 学生正常到校 | 教师默认勾选确认 | 可改为迟到/缺勤 |
| 迟到 | 学生迟到但到校 | 教师取消勾选后选择"迟到" | 可改为到校/缺勤 |
| 缺勤 | 学生未到校 | 教师取消勾选后选择"缺勤" | 可改为到校/迟到 |
| 请假 | 学生请假通过后自动标记 | 请假审批通过 | 不可更改（除非请假被撤销） |

**状态流转图**：

```
         ┌──────┐
         │ 未签到 │（排课完成后默认状态）
         └──┬───┘
            │ 教师签到
    ┌───────┼───────┐
    │       │       │
    ▼       ▼       ▼
 ┌────┐ ┌────┐ ┌────┐
 │到校│ │迟到│ │缺勤│
 └──┬─┘ └──┬─┘ └──┬─┘
    │       │       │
    └───────┼───────┘
            │ PC端修改（需权限）
            ▼
    任一状态可互相切换（保留修改日志）
    
    请假通过 → 签到状态自动变为"请假"（不可修改）
```

### 9.2 学生请假状态

| 状态值 | 含义 | 触发条件 | 后续操作 |
|:--:|------|---------|---------|
| 待确认 | 家长发起请假，等待教师确认 | 家长提交请假申请 | 教师确认/驳回 |
| 已通过 | 教师确认通过 | 教师点击"确认" | 标记签到 + 判断课时返还 |
| 已驳回 | 教师驳回 | 教师点击"驳回" + 填写原因 | 通知家长 |
| 已撤销 | 家长取消请假 | 家长在教师确认前取消（P2） | 恢复原状态 |

**超时处理（P2 迭代）**：
- 请假申请提交后 24 小时未被处理 → 自动提醒教师（消息推送）
- 48 小时未被处理 → 自动转给运营主管处理

### 9.3 教师请假状态

| 状态值 | 含义 | 触发条件 | 后续操作 |
|:--:|------|---------|---------|
| 待审批 | 教师提交请假，等待审批 | 教师提交请假申请 | 管理员通过/驳回 |
| 已通过 | 管理员审批通过 | 管理员点击"通过" | 冲突检测 → 逐节处理 |
| 已驳回 | 管理员驳回 | 管理员点击"驳回" + 填写原因 | 通知教师 |
| 已处理 | 通过 + 所有冲突排课处理完毕 | 所有冲突排课逐一处理完成 | 归档 |
| 已撤销 | 教师取消请假 | 教师在审批前取消（P2） | 恢复原状态 |

### 9.4 冲突排课处理状态

| 处理状态 | 含义 |
|:--:|------|
| 待处理 | 请假通过后、尚未选择处理方式 |
| 已代课 | 已指派代课教师 |
| 已调课 | 已更新排课时间 |
| 已停课 | 已取消排课并标记"待补课" |

## 10. 业务规则

### 10.1 签到规则

| 编号 | 规则 |
|:--:|------|
| S1 | 签到仅针对当天排课，不可提前或延后签到 |
| S2 | 同一排课同一学生仅有一条签到记录（唯一约束：`schedule_id + student_id`） |
| S3 | 签到需在排课开始时间之后才能操作（上课开始前 30 分钟到开始后 2 小时窗口内） |
| S4 | 已签到记录支持修改，PC 端权限控制（运营主管 / 校长），保留修改日志 |
| S5 | 学生已请假通过的情况下，签到自动标记"请假"，教师不可更改 |
| S6 | 签到操作人在签到记录中记录（教师姓名 + 操作端） |

### 10.2 学生请假规则

| 编号 | 规则 |
|:--:|------|
| L1 | 家长只能为自己关联的孩子请假（通过手机号绑定的学生） |
| L2 | 请假日期不允许选择过去日期 |
| L3 | 同一学生同一天不能重复请假（检查已有请假记录是否覆盖该日期） |
| L4 | 教师可以代任何本班学生请假，代请假直接通过 |
| L5 | 已驳回的请假，家长可修改后重新提交 |
| L6 | 请假通过后，如后续撤销（P2），需恢复签到状态并回退课时变动 |

### 10.3 教师请假规则

| 编号 | 规则 |
|:--:|------|
| T1 | 教师请假日期不允许选择过去日期 |
| T2 | 同一教师同一天不能重复请假 |
| T3 | 审批通过后不可直接撤销，需走审批驳回流程（P2） |
| T4 | 冲突检测仅检查状态为"正常"的排课，已取消/调课/停课的排课忽略 |
| T5 | 代课教师必须是：可授该科目 + 该时段空闲 + 非请假人 |
| T6 | 每个冲突排课必须选择一种处理方式，不可跳过 |
| T7 | 所有冲突排课处理完毕后，教师请假才算完整处理 |
| T8 | 调课后的新日期不能在该教师此次请假范围内 |

### 10.4 权限规则

| 操作 | 校长 | 运营主管 | 教师 | 家长 |
|------|:--:|:--:|:--:|:--:|
| 查看签到记录 | ✅ | ✅ | ✅(仅自己班级) | ❌ |
| PC 端签到操作 | ❌ | ✅ | ✅(仅自己班级) | ❌ |
| 小程序签到操作 | ❌ | ❌ | ✅ | ❌ |
| 代学生请假(PC) | ✅ | ✅ | ✅(本班学生) | ❌ |
| 学生请假(小程序) | ❌ | ❌ | ❌ | ✅(自己孩子) |
| 确认/驳回学生请假 | ❌ | ✅ | ✅(本班学生请假) | ❌ |
| 教师请假申请 | ✅ | ✅ | ✅(自己) | ❌ |
| 审批教师请假 | ✅ | ✅ | ❌ | ❌ |
| 处理冲突排课 | ✅ | ✅ | ❌ | ❌ |

## 13. 异常边界

### 13.1 签到异常

| 场景 | 处理 |
|------|------|
| 教师重复签到同一排课 | 后端唯一约束拦截，返回"该课程已签到"错误提示 |
| 签到时学生已退出班级 | 过滤已退出班级的学生，签到列表只显示在读学生 |
| 签到时排课已取消/停课 | 提示"该课程已取消，无法签到" |
| 签到窗口外操作 | 上课开始前 30 分钟到上课开始后 2 小时内允许签到；窗口外提示"不在签到时间段内" |
| 小程序网络断开 | 本地暂存签到数据，网络恢复后自动提交（P2） |
| 签到通知批量发送失败 | 签到主流程不受影响，失败的通知记录到失败队列，支持手动重发 |

### 13.2 请假异常

| 场景 | 处理 |
|------|------|
| 家长为学生请假，但该学生当天无排课 | 允许提交，但标注"该日期无排课记录"，教师仍可确认但不涉及签到标记和课时变动 |
| 请假日期跨多天，部分天无排课 | 仅对有排课的日期生效，无排课日期仅记录不影响任何数据 |
| 同一学生已被另一位家长提交了相同日期的请假 | 后端检测重复，返回"该日期已有请假申请待处理" |
| 学生请假通过后，排课被取消 | 请假保持已通过状态，签到标记和课时变动也保持 |
| 教师代请假时选的不是自己班的学生 | 运营主管可以代任何学生请假；教师只能代本班学生，非本班返回权限错误 |
| 学生请假驳回后，家长小程序重新提交 | 允许重新提交，作为新的请假申请处理 |

### 13.3 教师请假冲突异常

| 场景 | 处理 |
|------|------|
| 没有符合条件的代课教师 | 「代课」选项置灰或提示"无可代课教师"，必须选择「调课」或「停课」 |
| 代课教师资质不匹配 | 系统仅显示可授该科目的教师（通过教师档案的"可授科目"字段过滤） |
| 代课教师超出可授课时上限 | P2 迭代中引入教师课时上限配置，当前 MVP 不做限制 |
| 调课到新时间但教室冲突 | 调课时检验新时间+新教室的冲突，有冲突则阻止并提示具体冲突信息 |
| 调课到新时间与代课教师的其他排课冲突 | 仅调课不涉及更换教师，此场景不适用（调课保留原教师） |
| 并行处理冲突时，前一个代课教师被后续代课安排占用 | 冲突处理需逐节处理（前端引导顺序操作），避免并发冲突 |
| 教师请假天数内部分排课已有学生请假 | 正常处理，互不影响 |
| 停课后家长要求退费 | 走 M7 收银管理退费流程，不在本模块处理 |

### 13.4 课时返还异常

| 场景 | 处理 |
|------|------|
| 学生剩余课时不足（请假扣课时时） | 课时扣到 0 为止，不出现负数；记录日志 |
| 免费额度配置被误设为超大值 | 配置校验：free_limit 必须在 0-20 范围内 |
| 修改配置后，历史请假记录如何处理 | 不回溯处理已通过的请假，仅对新请假生效 |
