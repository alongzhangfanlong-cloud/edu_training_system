# M6 报名管理

> **模块定位**：核心教务层（P0），负责报名信息录入与报名列表管理，报名完成后自动流转至 M7 收银管理生成待收费条目。
> **后端模块**：`edu-module-enrollment`
> **前端路由**：`/enrollment/list`（报名列表）、`/enrollment/add`（报名录入），与 M7 在前端合并展示为「招生管理」菜单。

---

## 1. 模块概述

### 1.1 模块定位

M6 报名管理是「报名 → 收费 → 课时入账」业务链路的第一环，负责记录学生报名课程/班级的动作。报名提交后，系统自动在 M7 收银管理中生成一条「待收费」条目，由运营主管在 M7 中确认收费后，报名流程才算正式完成。

M6 不处理收费确认、退费、赠送课时等资金操作，这些全部归 M7 负责。M6 只关心"谁报了哪个课程/班级，多少钱，谁经手的"。

### 1.2 与 M7 的协作关系

```
┌─────────────────────────────────────────────────────┐
│                    M6 报名管理                        │
│                                                     │
│  录入报名 ──→ 生成报名记录 ──→ M7 生成待收费条目      │
│                     │                     │         │
│              报名状态：已报名         收费状态：待收费  │
│                     │                     │         │
│                     │              运营主管确认收费    │
│                     │                     │         │
│                     ▼                     ▼         │
│              报名记录关联收费ID      收费状态：已收费   │
│              不可编辑/取消          课时入账（M3）     │
└─────────────────────────────────────────────────────┘
```

| 协作环节 | M6 职责 | M7 职责 |
|----------|---------|---------|
| 报名录入 | 创建报名记录 + 创建待收费条目 | 消费待收费条目，确认收费 |
| 取消报名 | 标记报名取消 + 标记待收费条目为已取消 | 无需处理（待收费条目已取消） |
| 编辑报名 | 修改金额/课程（仅未收费） + 同步更新待收费条目 | 无需处理 |
| 收费确认 | 更新报名记录的收费状态为「已收费」 | 收到 M7 回调后更新 |
| 退费 | 更新报名记录的收费状态为「已退费」 | 收到 M7 回调后更新 |

**关键约定：**
- M6 创建待收费条目时通过 M7 提供的 Service 接口调用，不直接操作 M7 的数据表（遵循模块通信规范：跨模块通过 Service 接口通信）
- M7 确认收费/退费后回调 M6 提供的 Service 接口，更新报名记录的收费状态
- 前端合并展示：M6 的报名录入和报名列表与 M7 的收费管理、退费处理等共用「招生管理」菜单

### 3.2 表单字段详解

#### 3.2.1 基本信息区

| 字段 | 组件 | 必填 | 默认值 | 说明 |
|------|------|:--:|------|------|
| 经手人 | 只读文本 | ✅ | 当前登录用户姓名 | 自动填充，不可修改 |
| 报名日期 | el-date-picker | ✅ | 当天 | 可选择历史日期（补录），不可选择未来日期 |
| 备注 | el-input (textarea) | ❌ | 空 | 最多 200 字符，字数计数器显示 |

#### 3.2.2 报名明细区（批量报名表格）

每行代表一个"学生-课程-班级-金额"的报名条目，同一个学生可以添加多行，实现批量报名。

| 列 | 组件 | 必填 | 说明 |
|------|------|:--:|------|
| 课程 | el-select (远程搜索) | ✅ | 选择课程后自动带出默认价格，过滤班级下拉选项 |
| 班级 | el-select | ❌ | 仅显示所选课程关联的班级，可置空（报名课程但不入班） |
| 金额 | el-input-number | ✅ | 默认取课程单价，可手动修改（如折扣），最小 0.01，精度 2 位 |
| 操作 | el-button | — | 删除当前行，至少保留 1 行 |

**远程搜索规范（学生 + 课程）：**
- 学生搜索：应用「模式一：防抖 + 竞态」，300ms 防抖，searchSeq 竞态保护
- 课程搜索：同上，300ms 防抖 + 竞态
- 参见 `@docs/CLAUDE_front.md` 远程搜索规范

#### 3.2.3 学生选择区（仅当多行共享同一学生时显示在顶部）

由于批量报名场景下，同一个学生可能报多门课程，学生选择放在明细区上方。选择学生后，下方明细行都默认关联该学生。如果后续需要支持"一次提交多个学生的报名"，可扩展为每行独立选学生。

**学生快速新增：**
点击「+ 快速新增学生」按钮后，以弹窗形式打开简化的学生录入表单：

| 字段 | 组件 | 必填 | 说明 |
|------|------|:--:|------|
| 姓名 | el-input | ✅ | 2-20 字符 |
| 性别 | el-radio-group | ✅ | 男 / 女 |
| 手机号 | el-input | ❌ | 11 位数字 |
| 年级 | el-select | ❌ | 下拉选择 |
| 学校 | el-input | ❌ | 选填 |
| 家长姓名 | el-input | ❌ | 选填 |
| 家长手机号 | el-input | ❌ | 与家长姓名联动，至少填一个 |

弹窗提交成功后：
- 调用 M3 学生新增接口
- 关闭弹窗
- 自动将新学生选中为当前学生
- 刷新学生下拉列表

### 3.3 课程-班级联动逻辑

```
用户选择课程 ──→ 触发联动：
  ├── 1. 该行的金额自动填充为所选课程的单价
  └── 2. 班级下拉选项自动过滤为该课程关联的班级列表
         └── 班级下拉框显示格式：「班级名称（X/Y）」← X=已报人数，Y=最大人数
                  ├── 有剩余名额：正常显示
                  ├── 已满：选项置灰 + 标签"[已满]"
                  └── 若班级已满，用户仍可选择（允许超额报名，由主管判断）
```

**选择班级（可选）后的特殊处理：**
- 选择班级后，金额默认逻辑：优先取班级定价（如果班级有独立定价），否则取课程单价
- 班级名额检查：选择班级时，若班级已满（已报人数 >= 最大人数），在班级选择框旁显示橙色警告标签"该班级已满（当前 X/Y）"

### 3.4 金额默认逻辑

| 场景 | 金额默认值 | 是否可修改 |
|------|-----------|:--:|
| 仅选课程 | 课程单价 | ✅ |
| 选课程 + 选班级 | 班级独立定价（如有）→ 课程单价 | ✅ |
| 手动修改后 | 保留手动值 | ✅ |

金额校验规则：
- 最小 0.01 元（不允许 0 元或负数）
- 精度 2 位小数
- 提交时校验所有行金额之和 > 0

### 3.5 操作按钮

| 按钮 | 行为 | 状态 |
|------|------|------|
| 取消 | 有修改 → 弹窗确认"放弃已填写的内容？"；无修改 → 直接返回列表 | 默认 |
| 保存草稿 | 暂存表单数据（不触发业务校验），保留报名状态为「草稿」 | 默认（P1 可选） |
| 提交报名 | 校验 → 提交 → loading → 成功跳转列表 | 提交时 loading |

**保存草稿（P1 可选功能）：**
- 草稿不生成待收费条目
- 草稿可继续编辑后正式提交
- 草稿在列表中标记为「草稿」状态

### 3.6 提交流程

```
点击「提交报名」
  │
  ├── 前端表单校验
  │   ├── 学生是否已选
  │   ├── 报名日期是否有效
  │   ├── 明细表格至少 1 行
  │   ├── 每行的课程是否已选
  │   ├── 每行的金额是否有效（> 0）
  │   └── 是否有重复的课程+班级组合（同一学生）
  │       ├── 校验通过 → 继续
  │       └── 校验失败 → 错误提示，阻止提交
  │
  ├── 提交按钮 loading + 禁用
  │
  ├── 调用后端接口 POST /api/v1/enrollments/batch
  │   ├── 后端校验：
  │   │   ├── 学生是否存在
  │   │   ├── 课程是否上架
  │   │   ├── 班级是否存在且状态正常
  │   │   ├── 经手人是否存在
  │   │   └── 金额是否有效
  │   │
  │   ├── 创建报名记录（状态：已报名）
  │   └── 调用 M7 Service 创建待收费条目
  │
  ├── 成功：
  │   ├── Toast 提示"报名提交成功，已生成待收费记录"
  │   ├── 跳转回报名列表页
  │   └── 列表刷新
  │
  └── 失败：
      ├── 解除 loading
      ├── 显示具体错误信息
      └── 表单内容保留
```

### 3.7 状态处理

| 状态 | 处理方式 |
|------|----------|
| **加载中** | 页面顶部显示骨架屏（基本信息区灰色条块 + 表格骨架行 3 行），禁用提交按钮 |
| **学生下拉为空** | 下拉框显示"暂无学生数据"，提示"请先在学员管理中录入学生信息" |
| **课程下拉为空** | 下拉框显示"暂无课程数据" |
| **班级下拉为空** | 下拉框显示"该课程暂无关联班级，可跳过班级选择直接报名课程" |
| **班级已满** | 班级选项置灰 + 标签"[已满]"，仍可选择但显示橙色警告 |
| **提交 loading** | 提交按钮显示 spinner + "提交中..."，所有输入控件禁用 |
| **提交失败** | 保留表单数据，错误信息在页面顶部以 el-alert 展示（红色），不自动消失 |
| **网络超时** | 提示"网络请求超时，请重试"，保留表单数据 |

## 5. 报名 → 待收费 → M7 流转逻辑

### 5.1 完整状态机

```
                    ┌──────────┐
                    │   草稿   │ (P1 可选，保存草稿时的初始状态)
                    └────┬─────┘
                         │ 提交报名
                         ▼
     ┌──────────────────────────────────────┐
     │            已报名（待收费）            │
     │  报名记录状态=已报名                   │
     │  收费状态=待收费                       │
     │  → M7 存在关联待收费条目               │
     └────┬──────────────┬─────────────────┘
          │              │
          │ 取消报名     │ M7 确认收费
          ▼              ▼
    ┌──────────┐   ┌──────────┐
    │  已取消   │   │  已收费   │
    │ 待收费条目 │   │ 课时入账  │
    │ 标记为取消 │   │ (M3)     │
    └──────────┘   └────┬─────┘
                        │
                        │ M7 退费
                        ▼
                   ┌──────────┐
                   │  已退费   │
                   │ 课时扣回  │
                   │ (M3)     │
                   └──────────┘
```

### 5.2 流程步骤详解

#### Step 1：报名录入（M6）

- 运营主管在报名录入页填写学生、课程/班级、金额、经手人
- 提交后：
  - 创建 `enrollment_record`（状态：已报名）
  - 调用 M7 Service 接口 `createPendingTuition(enrollmentId, studentId, courseId, amount, handlerId)` → 创建 `tuition_record`（状态：待收费）
  - 将 M7 返回的收费记录 ID 回写到报名记录的 `tuition_record_id` 字段（或关联表）

#### Step 2：收费确认（M7 触发）

- 运营主管在 M7 收银管理中对该待收费条目执行「确认收费」
- M7 确认收费后回调 M6 Service 接口 `updatePaymentStatus(enrollmentId, PaymentStatus.PAID, tuitionRecordId)`
- M6 收到回调后更新报名记录的收费状态为「已收费」
- 此时报名流程完成，报名记录变为不可编辑/不可取消

#### Step 3A：取消报名（M6 触发，仅未收费）

- 运营主管在报名列表中点击「取消报名」
- 二次确认后：
  - 更新报名记录状态为「已取消」
  - 调用 M7 Service 接口 `cancelPendingTuition(tuitionRecordId)` → 标记待收费条目为「已取消」
  - 注意：取消报名不会触发退费（因为还没收费）

#### Step 3B：退费（M7 触发）

- 运营主管在 M7 中对已收费条目发起退费
- M7 退费完成后回调 M6 Service 接口 `updatePaymentStatus(enrollmentId, PaymentStatus.REFUNDED, tuitionRecordId)`
- M6 收到回调后更新报名记录的收费状态为「已退费」

### 5.3 M6 ↔ M7 接口契约

M6 暴露给 M7 的回调接口：

```java
// edu-module-enrollment 提供
public interface EnrollmentPaymentService {
    /**
     * 更新报名记录收费状态（由 M7 收费/退费完成后回调）
     * @param enrollmentId 报名记录 ID
     * @param status 目标状态：PAID（已收费）/ REFUNDED（已退费）
     * @param tuitionRecordId 关联的收费记录 ID
     */
    void updatePaymentStatus(Long enrollmentId, PaymentStatus status, Long tuitionRecordId);
}
```

M7 暴露给 M6 的调用接口：

```java
// edu-module-tuition 提供
public interface TuitionCreateService {
    /**
     * 创建待收费条目（由 M6 报名完成后调用）
     * @param enrollmentId 报名记录 ID
     * @param studentId 学生 ID
     * @param amount 收费金额
     * @param handlerId 经手人 ID
     * @return 收费记录 ID
     */
    Long createPendingTuition(Long enrollmentId, Long studentId, BigDecimal amount, Long handlerId);

    /**
     * 取消待收费条目（由 M6 取消报名时调用）
     * @param tuitionRecordId 收费记录 ID
     */
    void cancelPendingTuition(Long tuitionRecordId);

    /**
     * 更新待收费条目金额（由 M6 编辑报名金额时调用）
     * @param tuitionRecordId 收费记录 ID
     * @param newAmount 新金额
     */
    void updatePendingAmount(Long tuitionRecordId, BigDecimal newAmount);
}
```

## 6. 业务规则

### 6.1 报名规则

| 编号 | 规则 | 说明 |
|:--:|------|------|
| R1 | 学生校验 | 报名学生必须存在于 M3 学员管理中 |
| R2 | 课程校验 | 报名课程必须处于「上架」状态 |
| R3 | 班级校验 | 选择班级时，班级必须状态正常；班级已满给出警告但不阻止 |
| R4 | 金额校验 | 金额必须 > 0，不允许 0 元或负金额 |
| R5 | 经手人校验 | 经手人必须是系统有效用户 |
| R6 | 重复检查 | 同一学生对同一课程+班级组合，已存在未取消/未退费报名时，前端警告+后端拒绝 |
| R7 | 日期校验 | 报名日期不能是未来日期 |
| R8 | 批量提交 | 同一学生可在一次提交中报多门课程/班级 |

### 6.2 编辑规则

| 编号 | 规则 | 说明 |
|:--:|------|------|
| E1 | 编辑条件 | 仅收费状态为「待收费」或「草稿」的报名可编辑 |
| E2 | 已收费不可编辑 | 已收费/已退费的报名不可编辑，提示"已收费报名不可编辑，请通过收银管理处理" |
| E3 | 金额同步 | 编辑金额时，同步更新关联的 M7 待收费条目金额 |
| E4 | 学生不可变更 | 编辑时不可更换学生 |
| E5 | 编辑记录 | 编辑操作记录操作日志（AOP 自动记录） |

### 6.3 取消规则

| 编号 | 规则 | 说明 |
|:--:|------|------|
| C1 | 取消条件 | 仅收费状态为「待收费」或「草稿」的报名可取消 |
| C2 | 二次确认 | 取消前弹窗确认："确认取消该报名？关联的待收费记录将同步取消。" |
| C3 | 同步取消 | 取消报名时同步调用 M7 接口取消关联的待收费条目 |
| C4 | 不可恢复 | 取消操作不可撤销（前端提示明确告知） |

### 6.4 收费状态流转规则

| 编号 | 规则 | 说明 |
|:--:|------|------|
| P1 | 初始状态 | 报名提交后，收费状态初始为「待收费」 |
| P2 | 收费确认 | 由 M7 回调更新为「已收费」 |
| P3 | 部分收费 | 多收费条目场景，部分确认时状态为「部分收费」（此时仍可取消未收费的条目） |
| P4 | 退费 | 由 M7 回调更新为「已退费」 |
| P5 | 已取消 | M6 主动取消 → 「已取消」 |

## 7. 数据模型要点

### 7.1 核心表：enrollment_record（报名记录）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| student_id | BIGINT | 学员 ID（FK → M3 student） |
| course_id | BIGINT | 课程 ID（FK → M1 course） |
| class_id | BIGINT | 班级 ID（FK → M4 class），可为 NULL |
| amount | DECIMAL(10,2) | 报名金额 |
| handler_id | BIGINT | 经手人 ID（FK → sys_user） |
| enrollment_date | DATE | 报名日期 |
| payment_status | VARCHAR(20) | 收费状态：PENDING / PAID / PARTIAL / REFUNDED / CANCELLED / DRAFT |
| tuition_record_id | BIGINT | 关联的 M7 收费记录 ID，可为 NULL（草稿状态无收费记录） |
| remark | VARCHAR(200) | 备注 |
| create_time | DATETIME | 创建时间 |
| update_time | DATETIME | 更新时间 |
| is_deleted | TINYINT | 逻辑删除 |

**索引建议：**
- `idx_student_id`：按学生查询报名记录
- `idx_course_id`：按课程查询报名记录
- `idx_payment_status`：按收费状态筛选
- `idx_enrollment_date`：按报名日期范围查询
- `idx_handler_id`：按经手人筛选

### 7.2 辅助表：enrollment_class_detail（报名班级明细，如需要多行存储）

如果报名记录表采用「一条报名记录 = 一个学生 + 一个课程 + 一个班级」的粒度，则批量报名时每个课程对应一条 enrollment_record。这简化了数据模型，推荐采用此方案。

如果采用「一条报名记录 = 一个学生 + 多行课程明细」的粒度，则需要明细表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| enrollment_id | BIGINT | 报名记录 ID |
| course_id | BIGINT | 课程 ID |
| class_id | BIGINT | 班级 ID，可为 NULL |
| amount | DECIMAL(10,2) | 该明细的金额 |
| tuition_record_id | BIGINT | 关联的收费记录 ID |

**推荐方案：** 采用一条报名记录对应一个课程的方式（方案一），理由：
- 取消/编辑/收费粒度更清晰（每个课程独立管理生命周期）
- 与 M7 收费条目一对一关联更自然
- 列表展示时不用展开/折叠
- 批量提交时，前端展示为"共提交 N 条报名记录"

### 7.3 收费状态枚举

```java
public enum PaymentStatus {
    DRAFT,      // 草稿（P1 可选）
    PENDING,    // 待收费
    PARTIAL,    // 部分收费
    PAID,       // 已收费
    REFUNDED,   // 已退费
    CANCELLED   // 已取消
}
```

### 7.4 与 M7 的数据关联

采用关联字段模式：
- `enrollment_record.tuition_record_id` → 关联 M7 的 `tuition_record.id`
- 一对多场景（部分收费）：通过 `enrollment_id` 在 M7 中查询关联的收费记录

## 9. 异常边界

### 9.1 前端异常场景

| 编号 | 场景 | 处理方式 |
|:--:|------|----------|
| FE1 | 提交时网络断开 | 提示"网络连接失败，请检查网络后重试"，表单数据保留；如可能，localStorage 暂存 |
| FE2 | 学生下拉加载失败 | 下拉框显示"加载失败"，提供[重试]按钮 |
| FE3 | 课程下拉加载失败 | 下拉框显示"加载失败"，提供[重试]按钮 |
| FE4 | 班级下拉加载失败 | 默认显示空 "暂无班级数据"，不阻塞流程（可不选班级） |
| FE5 | 快速新增学生弹窗提交失败 | 保留弹窗，显示错误信息；不关闭弹窗 |
| FE6 | 重复提交（连点两次） | 按钮点击后立即 loading+禁用，前端防抖 1s |
| FE7 | 浏览器后退/刷新 | 有未保存数据时弹出浏览器原生确认（beforeunload 事件） |
| FE8 | 金额输入非法字符 | el-input-number 自动过滤非数字字符 |
| FE9 | 搜索无结果 | 显示友好空状态，不显示错误 |
| FE10 | 分页越界 | 自动修正到最后一页或首页 |

### 9.2 后端异常场景

| 编号 | 场景 | 处理方式 |
|:--:|------|----------|
| BE1 | 学生不存在 | 返回 400："所选学生不存在" |
| BE2 | 课程不存在或已下架 | 返回 400："课程「{name}」不存在或已下架" |
| BE3 | 班级不存在 | 返回 400："班级「{name}」不存在或已停用" |
| BE4 | 经手人不存在 | 返回 400："经手人不存在" |
| BE5 | 金额 ≤ 0 | 返回 400："报名金额必须大于 0" |
| BE6 | 同课程同班级重复报名 | 返回 400："该学生已报名此课程+班级组合，请勿重复报名" |
| BE7 | 编辑已收费的报名 | 返回 400："已收费报名不可编辑" |
| BE8 | 取消已收费的报名 | 返回 400："已收费报名不可取消，请通过收银管理处理退费" |
| BE9 | M7 待收费条目创建失败 | 事务回滚，报名记录不创建，返回 500："报名提交失败，请稍后重试" |
| BE10 | 数据库连接异常 | 返回 500："系统繁忙，请稍后重试"，记录 ERROR 日志 |
| BE11 | 并发修改冲突 | 乐观锁（version 字段）或悲观锁，返回 409："报名记录已被修改，请刷新后重试" |

### 9.3 M6 ↔ M7 协作异常

| 编号 | 场景 | 处理方式 |
|:--:|------|----------|
| ME1 | M6 调用 M7 创建待收费条目超时 | M6 事务回滚，报名记录不创建；前端提示"报名提交失败，请重试" |
| ME2 | M7 回调 M6 更新收费状态失败 | M7 侧重试机制（3次，指数退避）；最终一致性保证 |
| ME3 | M6 取消报名时 M7 待收费条目不存在 | 记录 WARN 日志，仅标记报名为已取消（数据不一致的容错处理） |
| ME4 | M7 退费已完成但 M6 状态更新失败 | M7 侧记录待处理的回调任务，支持人工触发的补偿机制 |
