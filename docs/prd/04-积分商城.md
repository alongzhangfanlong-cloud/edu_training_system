## 1. 模块概述

### 1.1 产品定位

积分商城是贯穿教务闭环的激励子系统，学生通过**签到出勤、获得好评、连续出勤**等正向行为获取积分，使用积分**兑换实物/虚拟礼品**。运营端负责礼品库管理与兑换核销，形成"行为激励 → 积分获取 → 礼品兑换 → 持续活跃"的正向循环。

### 1.2 核心价值

| 维度 | 价值描述 |
|------|----------|
| **学生端** | 学习行为被量化激励，出勤和表现好可获得实在奖励，提高续课意愿 |
| **教师端** | 教学评价可附带积分奖励，丰富课堂激励手段 |
| **运营端** | 礼品库灵活配置，兑换核销有据可查，积分消耗情况实时可见 |
| **机构端** | 低成本的学员激励体系，有效提升出勤率和满意度 |

### 1.3 模块边界

- **本模块负责**：积分账户管理、礼品库 CRUD、兑换流程处理、积分日志审计
- **本模块不负责**：签到行为本身（N07 考勤管理）、评价行为本身（N05 家校沟通）
- **依赖关系**：本模块接收来自 N07（签到积分）和 N05（评价积分）的事件写入，本身不反向依赖业务模块
- **小程序端**：P2 迭代中实现学生端礼品浏览与兑换下单（本 PRD 仅覆盖 PC 管理端）

### 1.4 菜单结构

```
🎁 积分商城                  ← N04（顶级菜单）
  ├── 积分礼品               ← N04.1  /points/gift
  └── 兑换记录               ← N04.2  /points/redemption
```

## 2. 积分系统设计（核心业务规则）

### 2.1 积分获取规则

积分获取仅支持**人工发放**，不设置自动触发机制。

| 来源 | 积分数 | 操作人 | 触发场景 | 备注 |
|------|:------:|--------|----------|------|
| **教师课后发放** | 自定义(有上限) | 教师 | 上完课后，教师在教学评价时附带积分奖励 | 每节课每个学生发放上限可配置（N08 系统配置），填写奖励原因，纳入积分日志；可选操作，不发也可 |
| **运维人员手动发放** | 自定义 | 运营主管/校长 | 在积分管理中单独给某学生增减积分 | 必须填写原因，完整审计日志；仅校长和运营主管可操作 |

### 2.2 积分核心规则

| 编号 | 规则 | 详细描述 |
|:----:|------|----------|
| **R01** | 积分不可透支 | 兑换前检查学生积分余额 >= 所需积分，余额不足时前端按钮置灰 + 后端返回 `INSUFFICIENT_POINTS` 错误码 |
| **R02** | 库存原子扣减 | 使用 `UPDATE edu_points_gift SET stock_remaining = stock_remaining - 1 WHERE id = ? AND stock_remaining > 0`，通过受影响行数判断库存是否充足 |
| **R03** | 取消兑换退积分+库存 | 事务包裹三个操作：① 兑换记录状态更新为 CANCELLED ② 积分账户 balance + 消耗积分 ③ 礼品 stock_remaining + 1，任一失败则全部回滚 |
| **R04** | 积分日志只追加 | `edu_points_log` 表的数据只增不删不改，任何人员（含管理员）不得直接修改日志记录，确保审计合规 |
| **R05** | 删除礼品前置校验 | 删除礼品时检查是否存在状态为 PENDING_CLAIM 的兑换记录，存在则禁止删除并提示"该礼品有 {count} 条待领取兑换记录，请处理后再删除" |
| **R06** | 禁用礼品不影响历史 | 已禁用的礼品不显示在小程序兑换列表和 PC 新增兑换中，但已有兑换记录仍正常展示和处理 |

### 2.3 积分变动类型枚举

| 类型码 | 含义 | amount 符号 | source_type | 说明 |
|--------|------|:-----------:|-------------|------|
| `EARN` | 获取积分 | 正数 | `TEACHER` / `ADMIN` | 教师课后发放或运维手动发放 |
| `REDEEM` | 兑换消耗 | 负数 | `REDEEM` | 兑换礼品时扣除 |
| `ADJUST` | 管理员调整 | 正数或负数 | `ADJUST` | 运维人员手动加减（含取消兑换退回） |
| `EXPIRE` | 积分过期 | 负数 | `EXPIRE` | 预留字段，v1 暂不启用积分过期机制 |

| 按钮 | 权限 | 行为 |

**交互约定**：

- 批量操作成功/失败均通过 `ElMessage` 提示

#### 3.4.2 操作按钮逻辑

| 操作 | 显示条件 | 行为 | 权限 |
|------|----------|------|:----:|
| **编辑** | 始终显示 | 打开编辑弹窗，预填当前数据 | `points:gift:edit` |
| **启用** | 当前状态为禁用 | 点击后即时切换 status 为 1，无确认弹窗 | `points:gift:edit` |
| **禁用** | 当前状态为启用 | 点击后即时切换 status 为 0，无确认弹窗 | `points:gift:edit` |
| **删除** | 始终显示 | 二次确认后调用删除接口 | `points:gift:delete` |

**删除确认弹窗**：
```
标题：删除确认
内容：确定删除礼品「{name}」吗？已有 {count} 条兑换记录将保留。
按钮：[取消] [确定删除]

特殊情况：
- 若存在未领取（PENDING_CLAIM）的兑换记录：禁止删除，提示"该礼品有 {count} 条待领取兑换记录，无法删除。请先完成核销后再操作。"
- 若 count 为 0：内容简化为"确定删除礼品「{name}」吗？删除后不可恢复。"
```

**启用/禁用即时切换**：
- 调用 `PUT /api/v1/points/gift/{id}/status`，请求体：`{"status": 1}` 或 `{"status": 0}`
- 成功：ElMessage.success('操作成功') + 表格刷新
- 失败：ElMessage.error(error.msg) + 不刷新表格

#### 3.5.4 提交逻辑

```
提交按钮点击：
  1. 表单校验（el-form.validate）
  2. 校验通过 → 提交按钮 loading=true
  3. 新增：POST /api/v1/points/gift
     编辑：PUT /api/v1/points/gift/{id}
  4. 成功：
     - ElMessage.success('操作成功')
     - 弹窗关闭
     - 表格刷新（编辑时保持当前页码，新增时跳转到第 1 页）

     - ElMessage.error(res.msg)
     - loading=false，弹窗不关闭，用户可修改后重新提交
```

#### 3.5.5 编辑模式特殊处理

- 库存数量字段在编辑时不显示（库存由系统管理，不可手动修改）。若要补货，通过单独的"库存调整"功能操作
- 礼品名称唯一校验时排除当前礼品自身 ID

### 4.4 标记已领取流程

```
时序：
  运营人员 → 点击"标记已领取" → 弹出确认框 → 确认

```

## 6. API 接口清单

### 6.1 通用约定

- 基础路径：`/api/v1/points`
- 认证方式：Bearer Token (JWT)，通过 `Authorization` 请求头传递
- 请求格式：`application/json`
- 响应格式：`{"code": 200, "msg": "ok", "data": {}}`
- 分页格式：`{"pageNum": 1, "pageSize": 10, "total": 100, "records": [...]}`
- 错误码规范：见下表

### 6.2 错误码定义

| 错误码 | HTTP 状态码 | 含义 |
|--------|:-----------:|------|
| `200` | 200 | 操作成功 |
| `400` | 400 | 参数校验失败 |
| `401` | 401 | 未登录或 Token 过期 |
| `403` | 403 | 无权限 |
| `404` | 404 | 资源不存在 |
| `409` | 409 | 业务冲突（如礼品名重复、状态不允许操作） |

| `INSUFFICIENT_STOCK` | 400 | 库存不足 |

## 9. 异常边界与并发控制

### 9.1 并发兑换库存超卖

**问题**：多名学生几乎同时兑换同一礼品，可能出现库存检查时均有库存，但扣减后总量为负。

**解决方案**：

```sql
-- 使用行锁 + 条件更新确保原子性
-- MyBatis-Plus XML Mapper 示例：

<update id="deductStock">
    UPDATE edu_points_gift
    SET stock_remaining = stock_remaining - 1
    WHERE id = #{giftId}
      AND stock_remaining > 0
      AND deleted = 0
</update>
```

```java
// Service 层处理
@Transactional(rollbackFor = Exception.class)
public void redeem(Long studentId, Long giftId) {
    // 1. 行锁锁定礼品记录
    PointsGift gift = giftMapper.selectByIdForUpdate(giftId);
    if (gift == null || gift.getStockRemaining() <= 0) {
        throw new BusinessException("INSUFFICIENT_STOCK", "库存不足");
    }
    // 2. 行锁锁定积分账户
    PointsAccount account = accountMapper.selectByStudentIdForUpdate(studentId);
    if (account.getBalance() < gift.getPointsRequired()) {
        throw new BusinessException("INSUFFICIENT_POINTS", "积分余额不足");
    }
    // 3. 扣减库存（条件更新，受影响行数=0 则超卖）
    int rows = giftMapper.deductStock(giftId);
    if (rows == 0) {
        throw new BusinessException("INSUFFICIENT_STOCK", "库存已被抢完");
    }
    // 4. 扣减积分
    accountMapper.deductPoints(studentId, gift.getPointsRequired());
    // 5. 创建兑换记录
    // 6. 写入积分日志
}
```

### 9.2 取消兑换事务一致性

**问题**：取消兑换涉及三张表的写操作，任一失败将导致数据不一致。

**解决方案**：Spring `@Transactional` 事务包裹全部操作，异常时自动回滚。

```java
@Transactional(rollbackFor = Exception.class)
public void cancelRedemption(Long redemptionId, Long operatorId) {
    PointsRedemption redemption = redemptionMapper.selectById(redemptionId);
    if (!"PENDING_CLAIM".equals(redemption.getStatus())) {
        throw new BusinessException("STATUS_NOT_ALLOWED");
    }
    // 1. 更新兑换记录状态
    redemption.setStatus("CANCELLED");
    redemption.setCancelTime(LocalDateTime.now());
    redemption.setOperatorId(operatorId);
    redemptionMapper.updateById(redemption);
    // 2. 退还积分
    accountMapper.refundPoints(redemption.getStudentId(), redemption.getPointsSpent());
    // 3. 写入积分日志
    PointsLog log = buildLog(redemption, "CANCEL_REDEEM");
    pointsLogMapper.insert(log);
    // 4. 恢复库存
    giftMapper.restoreStock(redemption.getGiftId());
    // 全部成功 → 事务提交
}
```

### 9.3 删除礼品前置校验

**问题**：删除有未完成兑换记录的礼品将导致核销无法关联。

**解决方案**：删除前校验 `COUNT(*) WHERE gift_id = ? AND status = 'PENDING_CLAIM' AND deleted = 0`，count > 0 则拒绝并返回错误码。

```java
public void deleteGift(Long giftId) {
    int pendingCount = redemptionMapper.countByGiftIdAndStatus(giftId, "PENDING_CLAIM");
    if (pendingCount > 0) {
        throw new BusinessException("GIFT_HAS_PENDING_REDEMPTION",
            String.format("该礼品有 %d 条待领取兑换记录，无法删除", pendingCount));
    }
    giftMapper.logicDelete(giftId);
}
```

### 9.4 积分日志只追加

**原则**：`edu_points_log` 表的所有操作仅限于 `INSERT`，任何人员（含 DBA）不得直接执行 `UPDATE` 或 `DELETE`。

**实现**：
- Mapper 层只暴露 `insert` 方法，不暴露 `updateById` / `deleteById`
- Service 层封装 `writeLog()` 方法，统一日志写入入口
- 通过数据库权限控制：生产环境只读账户无 INSERT/UPDATE/DELETE 权限
- 代码审查禁止日志表的任何修改操作

### 9.5 积分发放防重

**问题**：教师发放积分时可能因网络重试等原因重复提交。

**解决方案**：同一评价记录（source_type=TEACHER + source_id=评价ID）不重复发放积分，通过业务层面校验实现。

```java
public void earnPoints(Long studentId, Long teacherId, String sourceType, Long sourceId, int amount, String remark) {
    // 防重检查：同一评价记录已发过积分则跳过
    int exists = pointsLogMapper.countBySource(sourceType, sourceId);
    if (exists > 0) {
        log.warn("积分已发放，跳过：studentId={}, sourceType={}, sourceId={}", studentId, sourceType, sourceId);
        return;
    }
    // 校验教师发放上限
    int maxPerLesson = systemConfigService.getInt("points.teacher.max_per_student_per_lesson", 10);
    if (amount > maxPerLesson) {
        throw new BusinessException("超过单次发放上限：" + maxPerLesson);
    }
    // 正常发放逻辑...
}
```

### 9.6 异常场景汇总表

| 场景 | 前端处理 | 后端处理 | 返回码 |
|------|----------|----------|:------:|
| 积分余额不足 | 兑换按钮置灰 + tooltip 提示 | 事务内校验余额，不足抛出异常 | `INSUFFICIENT_POINTS` |
| 礼品库存不足 | 兑换按钮置灰 + 显示"已售罄" | 条件更新检查受影响行数 | `INSUFFICIENT_STOCK` |

| 删除有待领取的礼品 | 确认弹窗中明确提示禁止原因 | COUNT 查询校验 | `GIFT_HAS_PENDING_REDEMPTION` |
| 重复触发积分发放 | 无感知（后端自动去重） | source_type + source_id 查重 | 无异常，静默跳过 |

| 取消兑换时状态已变更 | "状态已变更，请刷新后重试" | 状态机校验 | `STATUS_NOT_ALLOWED` |

```java
    evaluation.getStudentId(),
    evaluation.getTeacherId(),
    "TEACHER",
    evaluation.getId(),
    bonusPoints,
    "课堂表现奖励"
);
```

### 10.4 教师发放上限配置

| 配置项 | 默认值 | 说明 |
|------|:--:|------|
| `points.teacher.max_per_student_per_lesson` | 10 | 教师每节课每个学生最多发放积分数 |

配置项存储在 N08 系统配置中，支持运营主管动态调整。
